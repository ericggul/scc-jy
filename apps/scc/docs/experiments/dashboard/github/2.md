# GitHub 2 — plane-to-surface input morph

- **Route:** `/github/2`
- **Date:** 2026-09-03
- **Baseline:** `/github/1`, preserved unchanged.
- **Variable:** wheel, trackpad, touch-drag, and keyboard input map a flat GitHub
  interface surface to a selected `cylinder` or `torus` target.
- **Observation state:** once the selected target is fully formed, Three.js
  `OrbitControls` enables mouse/touch orbit and pan while wheel input remains
  reserved for morphing.

## Participant and perceptual contract

A participant meets the GitHub home interface as a full-viewport, legible plane.
Wheel or trackpad movement, a vertical touch drag, and arrow keys continuously
change only the surface carrying that interface; the browser page and the
experiment container never scroll. The lower-right text row selects the target
topology and resets the input to its exact plane state. The visual task is to
perceive one materially continuous interface surface rather than an element
rotated like a card. At the terminal geometry, mouse drag and right-drag can
navigate the completed surface through the Three.js camera, while wheel and
trackpad vertical input continue to change the morph in either direction.

The first 6% of input holds an exact plane. `cylinder` makes the horizontal
coordinate a 2.32-radian vertical arc, retaining vertical coordinates. `torus`
maps the horizontal and vertical coordinates to the major ring and tube arcs of
a centered torus, then applies a shallow viewing yaw and tilt. Both targets use
the same fixed texture coordinate field, so the target choice changes geometry,
not the image attached to it. The canvas, fixed container, and document fallback
are black; the GitHub source surface retains its original dark-indigo field and
purple glow.

## Transferred rule and local adaptation

The Banpo-Xism mobile manifold links use an invisible scroll layer to drive a
continuous `blend` value, then mutate a segmented plane's vertex buffer while
retaining one texture coordinate field. Their Catenoid route interpolates each
vertex from its original plane coordinate toward a sampled 3D target; the input
is transport, not an overlay or a separate control.

This trial transfers that operative rule only:

```text
wheel / touch / keys → bounded input ref
  → 96×64 plane position buffer → selected target interpolation → one CanvasTexture
  → terminal target only: OrbitControls camera navigation
```

For the cylinder, a source point `(x, y, 0)` maps to
`x' = R sin(x/R)` and `z' = R(cos(x/R) - 1)` while `y` is retained. For the
torus, screen coordinates map to major angle `θ = 2πx / width` and tube angle
`φ = 2πy / height`, then to
`((R + r cos φ) cos θ, (R + r cos φ) sin θ, r sin φ)`. Intermediate states
linearly interpolate plane and selected-target positions after smoothstep input
mapping. The material is unlit so the same locally drawn GitHub 2D surface
remains the only readable image.

## Rendering record

question: whether an interface can retain its plane-relative hierarchy while a
bounded, non-scrolling input changes its topology from plane to cylinder or
torus.

source: Banpo-Xism's local Catenoid link and shared `SimpleSurfaceLinkPage`,
inspected 2026-09-03; [Three.js CanvasTexture](https://threejs.org/docs/pages/CanvasTexture.html),
[BufferAttribute](https://threejs.org/docs/pages/BufferAttribute.html), and
[PlaneGeometry](https://threejs.org/docs/pages/PlaneGeometry.html), accessed
2026-09-03; [Three.js OrbitControls](https://threejs.org/docs/pages/OrbitControls.html),
accessed 2026-09-03.

transfer: keep a fixed texture/UV field and mutate only a dynamic position
buffer from an input-owned ref, avoiding a React re-render for every input tick.

adaptation: `CanvasTexture` is drawn locally from the GitHub 1 visual contract;
its 96×64 `PlaneGeometry` updates only when input changes by 0.0001 or when the
selected target changes. `DynamicDrawUsage` is declared once. A native
non-passive wheel listener prevents page movement; document scrolling is locked
for this route and restored on unmount. At `SURFACE_MORPH_END`, Drei's installed
OrbitControls enables rotation and pan; its zoom is disabled so wheel/trackpad
vertical input remains the morph transport. No source image, GitHub asset,
Banpo-Xism asset, shader, post-process, or socket system is copied or introduced.

invariants: GitHub 1 remains unmodified; the initial hierarchy, colours, header,
hero, email form, and Copilot action stay recognisable as a single source image;
the only visible control is a lower-right `cylinder` / `torus` text row, using
the narrow selected-state contract of `face-voronoi/3`. No displayed progress
indicator, explanatory chrome, or visible camera-control widget is added.

evidence: model tests establish exact initial planarity for both targets, the
cylinder's fixed central axis and negative edge depth, torus closure around both
input axes, and the selected-target position writer.

rejected: CSS perspective alone, because it rotates one planar element rather
than giving the interface continuous cylindrical or toroidal coordinates; a
scrollable page/container, because it would confound spatial deformation with
content navigation; visible sliders or numerical readouts, because the target
selection is the only participant-facing parameter required for this trial.

next: compare whether the torus's seam and back-facing texture remain legible
enough to distinguish topology from arbitrary image distortion.
